## Critical

### C-01. A goal-form `consult/1` starts a fresh cycle stack, so a file that consults itself crashes ✔
- Status: open. True as reported, and more severe: it crashes at the default 8 MiB stack too (0.12 s), not only under `ulimit -s 1024`. The `use_module`/`ensure_loaded` sub-claim is false: their goal forms check `machine.prepared` (`file_ready`) and do not loop.
- Where: `src/machine/consult.cpp:57-60` (`load_consulted` passes no `shared_opening`), `src/machine/load.cpp:621-622` (`load_once` makes an empty `local_opening`), `src/machine/load.cpp:695` (`load_goal_term` passes `nullptr`, harmless there because of `prepared`).
- Repro: `self.pl` = `:- (true, consult('self.pl')).`, then `mosa -g "consult('self.pl')" -t halt` gives rc=139. So do `:- if(consult('selfif.pl')).`, mutual `a.pl`/`b.pl`, and `outer.pl` = `:- ['selfn.pl'].` where `selfn.pl` consults itself as a goal (the outer stack holds the key, but the goal load does not see it). `:- consult(F).`, `:- [F].` and `:- include(F).` give `file_cycle`.
- Also: `:- initialization(consult('selfi.pl')).` crashes too, but its goal runs after the text is closed, so passing the outer `opening` down will not catch it. It is unbounded nested loading, which iso-notes 7.1 lists as bounded by the native stack ("directives still start a nested `run_loop` per level").
- Expected: `file_cycle` diagnostic and a failed load, as for `[F]`.
- Standard: 7.4.2 (consult is not in 13211-1; behaviour is SPEC §5 / ADR 0026).
- Wave: W2. Gate: none.

### C-02. bagof/3 and setof/3 keep Template variables that existed before the call as the caller's cells ✔
- Status: open. Five of the six repros are real. The fifth (`findall(Y-L, bagof(T, (Y = f(T) ; Y = f(_)), L), R)` gives 2 groups) is correct: `_` is a free variable of the goal, so it is in the witness, and the witnesses `w(f(T1),A1)` and `w(f(A2),A2)` are not variants. The group split itself is real when the other variable is under `^`: `findall(Y-L, bagof(T, A^(Y = f(T) ; Y = f(A)), L), R)` gives `[f(_G1)-[_G1],f(_G2)-[_G3]]`, and 8.10.2 gives one group, `[f(_A)-[_A,_B]]`. Another case: `bagof(X-Y, (X = 1 ; X = 2), L)` gives `[1-_G1,2-_G1]`, with one shared `Y`.
- Where: `src/builtins/solutions.cpp:110-113` (`as_local`: a cell below `ids.base` that is not under `^` counts as external), used by `Encoder::start` (305) and `copy_var` (442).
- Repro: `bagof(X, true, X), acyclic_term(X)` fails (`X = [X]`). `bagof(A, (true ; true), [P, Q]), P == Q` succeeds, and `P == A` holds. `setof(B, (true ; true), L), length(L, N)` gives `N = 1`. `bagof(f(C, D), (C = a ; D = b), L), C = 1, D = 2` gives `L = [f(a,2),f(1,b)]`. `bagof(X, Y^(Y = X ; Y = X), L)` gives `[_G1,_G1]`, but `bagof(X, Y^(X = Y ; X = Y), L)` gives `[_G1,_G2]`.
- Expected: each solution is a fresh copy, as in findall/3: `X = [_]`; `P \== Q`; `N = 2`; `L = [f(a,_),f(_,b)]` whatever the later bindings; two distinct variables in both `^` cases.
- Standard: 8.10.2.1 and 8.10.3.1 (the iterated goal is run through findall/3, which copies). The 8.10.2.4 Examples still pass, because their answers are variants of the right ones.
- Wave: W2. Gate: none.

### H-01. IrTerm destruction allocates inside noexcept, so a bad_alloc there ends the process (read)
- Status: open. `release_deep` builds a `std::vector<std::vector<IrTerm>>` work stack. It is called from `IrTerm::release` (noexcept) and from the noexcept move assignment, for any tree deeper than 64. A `bad_alloc` there calls `std::terminate` instead of the heap-limit stop of ADR 0010. Not run: macOS does not enforce `ulimit -v`.
- Where: `src/core/ir.cpp:46-56` (`release_deep`), `67-74` (`IrTerm::release`), `90-102` (move assignment).
- Expected: destruction allocates nothing, for example by reusing the `args` buffers as the work list.
- Standard: not in 13211-1.
- Wave: W3. Gate: none (the caller's call). The fix keeps the IR and the ADR 0011 amendment 1 rule, which names IrTerm destruction (native recursion to depth 64, explicit stack below), and it is what ADR 0010 "Stop" already requires, so the plan's ADR gate does not seem needed.

### H-02. Unifying cyclic terms keeps a pair set outside the heap that grows as O(p·q) past --heap-max ✔
- Status: open, decision: ADR. As reported, and wider: `compare/3`, `==` and the other order predicates use the same pair memo (`PairSeen`, `src/builtins/order.cpp:43`) and grow the same way. Time is quadratic too.
- Where: `src/core/unify.cpp:29-45` (`Attempt::seen`), `61-86` (`unify_deep`); `src/builtins/order.cpp:43-64` (`PairSeen`).
- Repro: two cyclic lists of `a` with periods p and p+1, under `--heap-max 16`: `X = Y` at p=1000 takes 62 MB RSS (0.15 s), p=2000 238 MB (1.24 s), p=2800 467 MB (2.73 s), about 59 bytes per pair. `compare(O, X, Y)` and `X == Y` at p=2000 reach the same 238 MB. Extrapolated: p≈17,000 (about 34,000 list cells) reaches the reported 16 GiB.
- Expected: the walk stops at the heap limit, or works in about linear memory.
- Standard: not in 13211-1 (7.3.3 leaves cyclic terms undefined).
- Wave: W3. Gate: ADR. Counting the set against the limit would be another ADR 0010 amendment, as M6 and M17 were (amendments 2 and 3); union-find changes the algorithm of a hot walker of ADR 0011.

### H-04. The standard order of cyclic terms is not transitive, so sort/2 depends on the input order ✔
- Status: open, decision: ADR. A three-way cycle exists. No crash was seen, but `std::stable_sort` requires a strict weak ordering, so the call is undefined behaviour in C++.
- Where: `src/builtins/order.cpp:117-155` (`compare_head`), `158-182` (`compare_deep`, `compare_seen`: a pair seen before counts as equal); `src/builtins/lists.cpp:73, 163` (`std::stable_sort`).
- Repro: `A = f(A, b), B1 = f(B1, b), B = f(B1, B), C = f(C1, C), C1 = f(C, a)` gives `compare` `<` for (A,B), (B,C) and (C,A). `sort([A,B,C], S1), sort([C,B,A], S2)` gives `S1 \== S2`.
- Expected: a total order on cyclic terms, or at least a sort that does not depend on the input order.
- Standard: not in 13211-1 (7.2 orders finite terms; 7.3.3).
- Wave: W3. Gate: ADR (a new definition of the order of cyclic terms). Note: an M-27 fix that moves setof/3 to `std::sort` would bring this undefined behaviour into setof/3.

### H-08. Past 63,488 slots a cyclic goal through call/N, catch/3, once/1, \+/1 or if/3 is not found and runs again and again ✔
- Status: open. True as reported. Past `kDeferAt` the rest of a run-time goal becomes a late `call/1` leaf (M28). `blocks` follows only `, ; -> *-> :`, so a cycle through a leaf is not seen as blocking, and `late_goal` only calls `note_back` on the root of the deferred part, which misses the back edge. The deferred translation defers again, so the cycle is never found. A cycle through `,` alone is still found (`blocks` treats a cyclic skeleton as blocked). This is not one of the open-items "Known limits of the cyclic-goal checks", and no owner decision of 2026-11-17 accepts it as a limit (decision A asks for the error).
- Where: `src/machine/compile.cpp:91-97` (`skeleton_children`), `162-178` (`late_goal`), `181-216` (`blocks`, `defers`), `248-250` (`note_back`), `285-286` and `326-327` (callers).
- Repro: `h08.pl`, `G = (bump, Body)` where Body is N copies of `nonvar(f(1))` ending in Tail and `bump` counts and fails on its third run. With N = 100 every Tail raises `resource_error(cyclic_term)`. With N = 70000, `Tail = (true, G)` still raises, but `call(G)`, `catch(G, _, true)`, `once(G)`, `\+ G` and `if(true, G, true)` give `failed-passes(3)`: the goal ran its side effect three times. - Expected: the error found as at N = 100. That is before anything runs for the `,`, `call`, `catch`, `once` and `\+` tails. For the `if/3` tail it is when the `if/3` runs, per the if/3 decision: at N = 100 that tail gave `passes(1)`.

- Wave: W4. Gate: none.

### H-09. A catch/3 whose Goal has a variable in goal position catches its own cyclic-goal error ✔
- Status: open, question. The behaviour is as reported, and the mechanism is the documented one. `runs_late` makes such a Goal a late `Call` leaf (ADR 0014), and `late_goal`'s `note_back` does not walk into the Goal's connectives. The cycle is found when that leaf runs, which is inside the armed catch, so the catch receives the error and runs Recovery. The explicit spelling `G = catch(call((true, G)), C, true)` behaves the same way, which is the recorded leaf rule of iso-notes 7.3.3 ("found when the leaf runs and translates it"). M15 (iso-notes 7.8.9) records the same pattern for `type_error`: `catch((write(a), 1), E, true)` binds `E`. On the other side, decision A says the error comes "before any part runs", and `m13_catch_cycle` in `tests/pl/control.pl` says a catch inside the cycle does not receive it. That row differs from this repro only by the unbound `X`, which never runs. Which of the two wins is an owner choice. Telling the compiler's own leaf apart from a leaf the user wrote is this triage's reading, not a recorded rule. Writing `a` first is not extra severity: `X = (write(a), \+ (write(b), X))` also writes `a` before the error, under the documented leaf rule.
- Where: `src/machine/compile.cpp:128-133` (`runs_late`), `162-178` (`late_goal`), `248-250` (`note_back`).
- Repro: `G = catch((X, G), C, true), catch(call(G), E, true)` gives `C = error(resource_error(cyclic_term), _)` with `E` unbound (the caller's run: `call(G)` succeeds). With `X = true` bound first, or with `catch((true, G), C, true)`, `E` gets the error and `C` stays unbound. `G = catch(call((true, G)), C, true)` gives the same result as the `X` form.
- Standard: 7.3.3 (undefined); iso-notes 7.3.3 decision A (2026-11-17), 7.8.9 (M15) and ADR 0014.
- Question: A (keep: the late Goal runs as call/1 inside the catch, as in M15 and the leaf rule, so the catch receives the cyclic-goal error) or B (`late_goal` walks the connectives of a late catch Goal so the outer call/1 raises before the catch is armed, as `m13_catch_cycle` expects)?
- Wave: W4. Gate: question.

### H-20. Under some char_conversion mappings, read/1 from user_input waits for more input after a complete term ✔
- Status: open. The mapping must make the last character of a quoted token or of a block comment a layout char or `%` outside quotes, for example `q` to `'` and `'` to a space. Suppose a scout resumes inside a quote (`Inside::Quote`) and the quote closes on the last byte. `scout` then stores `Scout{lexer.item_}`, but `item_` is stale: it was set to `state.from`, and `skip_ignorable` does not update it at the end of the source. The next scout therefore restarts inside the quote with `Inside::None`. In the repro it lands on the `%` and takes the rest as a line comment, so read/1 blocks until another full stop or EOF arrives. The report's point that `''` cannot be seen ahead is part of the cause, since a closing `'` on the last byte may be half of `''`. The block-comment sub-claim is true as well: a block comment that a scout resumes and that closes on the last byte leaves the same stale `item_`. The cases were found with a simulator linked against `build/libmosa.a` (`scout_sim.cpp` in this directory). It feeds input byte by byte through the real `Lexer::may_end_before_last`, `Lexer::scout` and `Reader`, as `pull_to_mark` and `intake_term` do. Over 177,155 inputs for each mapping, it found one hang each for `q`→`'` with `'`→space and for `q`→`'` with `'`→`%`. It found none with no conversion, and none for the 6 other mappings of that run. An earlier pass of 9,330 inputs had no `%` in its alphabet and found nothing.
- Where: `src/read/lexer.cpp:292-315` (`Lexer::scout`; line 308 stores `item_`), `src/read/lexer.cpp:189-191` (`skip_ignorable` sets `item_` only inside its loop), `src/read/lexer_literal.cpp:392-402` (`quoted_body` closes on a quote at the end of the source).
- Repro: `(printf "X = q.%%.'. \n"; sleep 6) | timeout 3 mosa -g "set_prolog_flag(char_conversion,on), char_conversion(q,''''), char_conversion('''',' '), read(T), writeq(got(T)), nl" -t halt` exits 124 with no output. - Expected: read/1 returns `X = '.%.'` (or `X = a`) as soon as `. ` arrives.
- Standard: 8.14.1, 7.11 (flag char_conversion).
- Wave: W5. Gate: none.

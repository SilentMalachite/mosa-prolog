# Benchmarks

`mosatest --bench <file> [--count <N>] [--work <directory>] [--cmake <path>] [--report <file>]` runs `bench(N)` five times in the interpreter (`mosa <file> -- N`) and five times in the executable that `mosac emit` + CMake (Release) builds from the same file, then prints the wall-clock median of each side and the ratio (interpreter time divided by translated time). Each run is one whole process, from start to exit, so both sides include process start-up and the loading of the source in the same way. `N` is the same on both sides (default 20000). The emitted project, its build and the logs go under `--work` (default: `mosatest-bench` next to the `mosatest` executable, in the build tree); only the child directory `mosatest-bench-out` is removed and recreated. With `--report <file>`, the result is also written to that JSON file in the form of [`bench.json`](bench.json): one line per program, keyed by the file name as given; the line for the same file is replaced and the other lines are kept. The programs in `bench/` define `bench(N)` as a failure-driven loop, check their first solution before running it, and read `N` from the flag `argv`; `statistics/2` is not used, so the programs measure the whole process and no GC counter is read. The GC is described in [Cost of the GC](#cost-of-the-gc).

## Memory in long loops

This is the check for the first phase 7 exit criterion of SPEC section 9, "memory usage plateaus in long-running loops". It was measured on 2026-11-10 on the same machine at commit 0b6e63f, Release, with the default limit (4 GiB) and no `MOSA_GC_STRESS`. Each loop below runs N, 10N and 100N times in one process, both in `mosa file.pl -- Shape N` and in the executable that `mosac build` makes from the same file (`./exe Shape N`), and `/usr/bin/time -l` gives the maximum resident set size of the whole process. The file has `:- initialization(main, main).`, `:- use_module(library(between)).`, `:- dynamic(cnt/2).`, the usual `member/2` and `append/3`, and `mk(K, I, L)`, which builds a list of K terms `f(K, I, g(K))`. Each loop body other than `fail` and `repeat` is the clause before `N1 is N - 1` and the recursive call:

```prolog
count:   true
build:   mk(100, N, L), length(L, 100)
fail:    ( between(1, N, I), mk(50, I, _), fail ; true )
findall: findall(X-N, member(X, [a, b, c, d, e, f(N), g(N, N)]), L), length(L, 7)
assert:  assertz(cnt(N, f(N, [N, N]))), retract(cnt(N, _))
catch:   catch(throw(e(N, [N])), e(_, _), true)
codes:   number_codes(N, Cs), atom_codes(abc, Ds), append(Cs, Ds, Es), length(Es, _)
copy:    copy_term(f(X, Y, [X, Y, N]), T), T =.. [_|As], length(As, 3)
repeat:  repeat, retract(cnt(k, I)), I1 is I + 1, assertz(cnt(k, I1)), mk(20, I, _), I1 >= N, !
```

Single runs of the interpreter were sampled every 5 seconds with `ps -o rss`. `findall` with N = 2 × 10^7 (170 s) reached 18,048 KiB at 30 s, rose once to 18,544 KiB at 105 s and held it to the end. `assert` with N = 10^8 (210 s) held 17,904 KiB from 5 s to 115 s, then rose in three steps to 19,456 KiB and ended while still rising. ## CI

The macOS job runs all seven programs with the `N` of each line of `bench.json` and writes a table of the new times, the new ratio and the committed ratio to the Job Summary. It compares ratios (interpreter time divided by translated time), not milliseconds: both sides of a ratio run on the same runner, so the runner's speed cancels out, while the GitHub macOS runner's absolute times differ from the machine above by 20–80%. When a program's ratio is 20% or more below its committed ratio, the step prints a `::warning::` annotation and marks the row. When a measured or committed ratio is missing or zero, it prints a `::warning::` that the comparison was skipped. The step has a 20-minute timeout and never fails the job; it is a coarse regression alarm, not a measurement. It cannot see a slowdown of the Big arithmetic: `bigint` spends both sides in the same libmosa code, so its ratio stays about 1.0 however slow that code gets.

## Interpreter limits seen while choosing N

These were found before the GC (phase 6), when the heap was 1<<20 words and never collected. They explain why `N` and `tak(17, 11, 6)` look the way they do; with the GC the heap grows up to the limit (`--heap-max`, default 4 GiB) and is collected, so `tak(18, 12, 6)` and a bare `loop(1000000)` now run in 1 MiB (see the README). The programs and `N` were kept so that the numbers stay comparable.

- `tak`: the usual `tak(18, 12, 6)` (63609 calls) ran out of heap in a single call, so the program uses `tak(17, 11, 6)` (16701 calls, result 7). `main` runs `check` inside `\+ \+` to give its heap back before `bench(N)`.
- `loop/1` itself: each level of the recursion left a choice point and what it used stayed on the heap; a bare `loop(N), fail` ran out of heap between N = 40000 and 45000. This bounded `deriv`, the cheapest iteration, to N = 30000.

## queens

`bench/queens.pl`: all 92 solutions of 8 queens, placing one queen per column and checking the diagonals against the queens already placed (`sel/3`, `attack/3`, `\+`). The check is that the first solution is the lexicographically first one, 1,5,8,6,3,7,2,4 by column (the list holds the last-placed queen first).

## zebra

`bench/zebra.pl`: the five-houses puzzle, solved by unifying `house/5` terms against a list with `mem/2`, `right_of/3` and `next_to/3`. The search runs to the end on every iteration although there is one solution. The check is the whole known solution (the Japanese keeps the zebra, the Norwegian drinks water).

## tak

`bench/tak.pl`: the Takeuchi function `tak(17, 11, 6)` (see above for the size): integer arithmetic, comparison, and deterministic recursion with a cut. The check is that the result is 7.

## deriv

`bench/deriv.pl`: Warren's symbolic differentiation of four expressions per iteration (`ops8`, `divide10`, `log10`, `times10`), building and dropping terms. The check compares the derivative of `ops8` and of `x * x * x` with the terms worked out by hand.

## crypt

`bench/crypt.pl`: the multiplication puzzle OEE × EE = OOEE with partial products EOEE and EOE (E even, O odd digits), searched in full with digit lists (least significant first) and integer arithmetic. The check is the unique solution 348 × 28 = 9744 with partial products 2784 and 696.

## bigint

`bench/bigint.pl`: arbitrary-precision integers (phase 10, ADR 0025). Each iteration computes `7^7^7` (an integer of 2,311,978 bits) and its `msb`, then 1000! by 1000 multiplications (`fact/2`) and its decimal digits with `number_codes/2`. `7^7^7` is not converted to text: `number_codes` of it takes about 12 s (quadratic, a design non-goal) and would measure only the conversion. The check is that `msb(7^7^7)` is 2311977 and `7^7^7 mod 1000000007` is 930034226 (the `msb` sees only the top bits), and that 1000! has 2568 digits whose sum is 10539, all values computed with Python. One iteration takes about 0.16 s and almost all of it is the power: in the interpreter, 10 iterations of the power and `msb` alone took 1.60 s and 100 iterations of 1000! with `number_codes` 0.16 s (wall time of `mosa`, start-up included). Both sides spend that time in the same C++ code of libmosa, so the ratio is about 1.0; the row follows the Big arithmetic, not the translation.

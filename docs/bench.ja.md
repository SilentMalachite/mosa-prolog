# ベンチマーク

この文書は [英語版](bench.md) の日本語訳である。食い違うときは英語版に従う。

`mosatest --bench <ファイル> [--count <N>] [--work <ディレクトリ>] [--cmake <パス>] [--report <ファイル>]` は、同じファイルの `bench(N)` をインタプリタ（`mosa <ファイル> -- N`）で 5 回、`mosac emit` + CMake（Release）で作った実行ファイルで 5 回流し、それぞれの壁時計の中央値と比（インタプリタの時間を翻訳の時間で割った値）を出す。1 回は起動から終わりまでの 1 つのプロセスなので、両側とも起動と原文の読み込みの時間を同じように含む。`N` は両側で同じ（既定は 20000）。出した目録とそのビルドとログは `--work` の下に置く（既定は `mosatest` の実行ファイルの隣、ビルド木の `mosatest-bench`）。消して作り直すのは子ディレクトリ `mosatest-bench-out` だけである。`--report <ファイル>` を渡すと、結果を [`bench.json`](bench.json) の形でその JSON ファイルにも書く。1 プログラム 1 行で、鍵は渡したままのファイル名である。同じファイルの行は置き換え、ほかの行は残す。`bench/` のプログラムは `bench(N)` を失敗駆動の繰り返しで定義し、流す前に最初の解を確かめ、`N` を旗 `argv` から読む。`statistics/2` は使わないので、プログラム全体の時間を測り、GC の数は読まない。GC の費用は [GC の費用](#gc-の費用) に書く。

## 結果

2026-11-02（フェーズ7、ADR 0015 で節の置き場と第1引数の索引を入れたあと）に Apple M1 Max、macOS 27.2、Apple clang 21.0、Release ビルドで測った。時間は 5 回の中央値（ミリ秒）である。[`bench.json`](bench.json) が同じ数を持つ（`--report` が生成する。手で直さない）。

| プログラム | N | インタプリタ (ms) | 翻訳 (ms) | 比 |
| --- | ---: | ---: | ---: | ---: |
| nrev | 20000 | 3407 | 128 | 26.6 |
| queens | 80 | 2756 | 442 | 6.2 |
| zebra | 120 | 1954 | 782 | 2.5 |
| tak | 100 | 1380 | 302 | 4.6 |
| deriv | 30000 | 928 | 127 | 7.3 |
| crypt | 300 | 1216 | 321 | 3.8 |

`N` はプログラムごとに、インタプリタ側が 1〜3 秒ほど、翻訳側が 0.1 秒以上になるように選んだ。測り直して `bench.json` を書き直すには、リポジトリ直下で次を実行する。

```sh
for run in nrev:20000 queens:80 zebra:120 tak:100 deriv:30000 crypt:300; do
  LANG=C build/mosatest --bench bench/${run%%:*}.pl --count ${run#*:} --work tests/tmp/bench --report docs/bench.json
done
```

翻訳側はフェーズ6 Task 13 の時点で `mosac emit` が出すコードを、この計測のために変えずに使った。フェーズ6の完了条件（SPEC 第9節: 翻訳した `nrev` がインタプリタの 3 倍以上速い）を満たす。ほかの比は `nrev` より低い。フェーズ6ではそれらに向けて翻訳のコードを調整していない。

どのプログラムも `tests/pl/bench_<名前>.pl` が include し、最初の解の確かめと `bench(2)` をテストとして流す。これで `mosatest tests/pl` が期待する解を確かめ、差分テスト（`mosatest --diff tests/pl`、CTest の `diff_tests_pl`）がインタプリタと翻訳したコードを比べる。6 本とも一致し、すべての述語に生成関数が付く。

## GC の費用

2026-10-30 に同じ機械で、木を 1 つずつ測った。GC を入れる前の最後のコード（コミット b5303e5）と GC のブランチを、どちらも Release、同じ `N`、5 回の中央値（ms）で比べる。差は b5303e5 に対する GC のブランチの値である。ホットな道に足したのはインタプリタの各歩の前の検査（`gc_safe_point`）とヒープの確保の分だけで、検査は比較 1 回（`heap.size() >= gc_trigger`。`gc_trigger` は `MOSA_GC_STRESS` が有効なときだけ 0）、確保の速い道も比較 1 回で、どちらも呼び出しにならないよう inline で定義した。`nrev` の行は最終の測定で、コミット 816c99e のあとに測り直した。木ごとに 3 回、交互に測った中央値である（GC 前のインタプリタ 3185、3172、3169 ms に対し今は 3272、3268、3267 ms、翻訳は 144、143、144 に対し 132、132、131）。ほかの 5 行は、816c99e の直前の全体の測定から取った。816c99e が触れたのは比較 1 つだけである。

| プログラム | インタプリタ 前 | インタプリタ 今 | 差 | 翻訳 前 | 翻訳 今 | 差 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| nrev | 3172 | 3268 | +3.0% | 144 | 132 | -8.3% |
| queens | 2834 | 2929 | +3.4% | 626 | 618 | -1.3% |
| zebra | 2833 | 2843 | +0.4% | 1070 | 1033 | -3.5% |
| tak | 2502 | 2516 | +0.6% | 321 | 326 | +1.6% |
| deriv | 1137 | 1125 | -1.1% | 155 | 152 | -1.9% |
| crypt | 3084 | 3132 | +1.6% | 332 | 324 | -2.4% |

GC のブランチを最初に測ったときは、`nrev` がインタプリタで 16%、翻訳側で 75% 遅かった。原因はホットな道の 2 つの呼び出し（ヒープの `allocate` と `AddressRange::words()` が呼び出しになっていた）で、両方を inline にした結果が上の表である。816c99e の前は、インタプリタの `nrev` が全体の表で +8.3%、繰り返しの測定で +3.4% と +5.6% だった（安全点の検査が比較 2 つだった）。比較 1 つにしたあとは +3.0% で、5% 以内である。残る差はこれ以上プロファイルしていない。既定の上限では 6 本のどれも回収が 1 度も走らない。`bench(N)` を 1 回流したあとの `statistics(garbage_collection, G)` はどれも `[0,0,0]` だった。このため、数字に回収の時間は入っていない。

## 小さな節の vector の費用

2026-11-04 に同じ機械で、どちらも Release で、2 つの木を並べてビルドして測った。「前」は 60c50e7、「今」はレビュー M21（ADR 0015 の改訂 2。16 節までの述語は節を長さぴったりの vector に、それより長い述語は deque に置く。libc++ で `Predicate` は 304 から 288 バイトに、`Snapshot` は 128 から 112 に減る）。メモリは `mosa file -g goal -t halt` の `/usr/bin/time -l` の最大 resident set size（macOS、libc++）を 3 回測った中央値。1 節の述語 4 万個は `p0(0).` から `p39999(39999).`、1 つの述語は `q(0).` から `q(39999).` である。

## CI

macOS のジョブは 6 本を `bench.json` の各行の `N` で流し、新しい時間と新しい比とコミット済みの比の表を Job Summary に書く。比べるのはミリ秒ではなく比（インタプリタの時間を翻訳の時間で割った値）である。比の両側は同じランナーで動くのでランナーの速さが消えるが、GitHub の macOS ランナーの絶対時間は上の機械と 20〜80% 違う。プログラムの比がコミット済みの比より 20% 以上下がれば、手順は `::warning::` の注記を出し、その行に印を付ける。測った比かコミット済みの比が無いか 0 なら、比較を飛ばしたという `::warning::` を出す。この手順は 20 分で打ち切り、ジョブを失敗させることはない。退行の粗い目安であり、計測ではない。

## N を選ぶときに見えたインタプリタの上限

以下は GC の前（フェーズ6）、ヒープが 1<<20 語で回収されなかった時期に見えたことである。`N` と `tak(17, 11, 6)` の形の理由を説明する。GC のあとはヒープが上限（`--heap-max`、既定 4 GiB）まで伸びて回収されるので、`tak(18, 12, 6)` も素の `loop(1000000)` も 1 MiB で走る（README を見よ）。数字を比べられるよう、プログラムと `N` は変えていない。

- `tak`: よく使う `tak(18, 12, 6)`（63609 回の呼び出し）は 1 回でヒープが尽きたので、`tak(17, 11, 6)`（16701 回、結果は 7）を使う。`main` は `check` を `\+ \+` の中で呼び、`bench(N)` の前にそのヒープを返す。
- `loop/1` そのもの: 再帰の各段が選択点を残し、その段が使った分はヒープに残った。素の `loop(N), fail` は N が 40000 から 45000 の間でヒープが尽きた。1 回が最も軽い `deriv` はこれで N = 30000 に抑えた。

## queens

`bench/queens.pl`: 8 王妃のすべての解（92 個）。1 列に 1 つずつ置き、置いた王妃との斜めの利きを確かめる（`sel/3`、`attack/3`、`\+`）。確かめるのは、最初の解が辞書順で最初の解、列ごとに 1,5,8,6,3,7,2,4 であること（リストは最後に置いた王妃から並ぶ）。

## zebra

`bench/zebra.pl`: 5 軒の家の謎。`house/5` の項をリストに `mem/2`、`right_of/3`、`next_to/3` で単一化して解く。解は 1 つだが、どの回も探索を最後まで続ける。確かめるのは、よく知られた解の全体（シマウマを飼うのは日本人、水を飲むのはノルウェー人）である。

## tak

`bench/tak.pl`: 竹内関数 `tak(17, 11, 6)`（大きさは上を見よ）。整数の算術、比較、切りでの決定的な再帰。確かめるのは結果が 7 であること。

## deriv

`bench/deriv.pl`: Warren の記号微分。1 回に 4 つの式（`ops8`、`divide10`、`log10`、`times10`）を微分し、項を作っては捨てる。確かめるのは、`ops8` と `x * x * x` の導関数が手で求めた項と一致すること。

## crypt

`bench/crypt.pl`: 掛け算の覆面算 OEE × EE = OOEE、部分積は EOEE と EOE（E は偶数、O は奇数の数字）。数字のリスト（下の桁から）と整数の算術で全探索する。確かめるのは唯一の解 348 × 28 = 9744、部分積 2784 と 696 である。

# フェーズ7 GC 設計

日付: 2026-10-30
状態: 承認済み（2026-10-30）

## 意図

負荷テストが途中で `heap_limit` で止まるため、最後まで走ったときの所要時間が見通せない（所有者）。フェーズ7の最初の仕事として、ヒープのゴミを回収する GC を入れ、ヒープを必要に応じて自動で伸ばし、伸ばせないときは安全に止める。GC が働いていることを統計値で見えるようにする。

読む人は、このあと実装計画を書き、実装するエージェントである。

## 規模と順序

フェーズ7の仕事は互いに独立している。この文書は GC だけを扱う（`garbage_collect/0` と `statistics/2` を含む）。残りは GC の後に、それぞれ別の設計で扱う（提案順、私の判断）。

1. GC（この文書）
2. writer と loader の反復化（深い項・長いリストで C++ スタックがあふれる件。GC とは別のスタックの問題）
3. MSVC の Debug（/MTd）の libmosa が `mosac build` でリンクできない件
4. 日英マニュアル
5. `mosac dist` とリリースパッケージ

## 目標

- 合格の目安は、メモリの絶対値ではない（環境で変わるため、所有者）。同じ処理を繰り返しても使用量が増え続けず、頭打ちになること（SPEC 第9節のフェーズ7の完了条件と同じ）。
- 物差しは次の 2 つ（所有者が了承）。どちらも、今は途中でヒープがあふれる。
  - `tak(18,12,6)`
  - 素朴な決定的ループ `loop(N)`。今は N が 40000〜45000 の間であふれる
- 生きているデータが本当に大きいとき、ヒープは自動で伸びる（所有者）。
- 伸ばせないときは、エラーメッセージを出して安全に止まる（所有者）。
- GC の統計値を表示できる（所有者）。`statistics/2` と、GC のたびに 1 行出すログの旗の 2 つで見せる。
- インタプリタと mosac が翻訳したコードの両方で同じように効く。差分テストの一致を崩さない。

## 非目標

- 世代別・増分・並行の GC。スレッド。
- ヒープを縮めること。一度伸びた容量は、プロセスが終わるまで保つ。
- アトム表の GC。ループでアトムを作り続けると表は伸び続ける。これは既知の制限として `docs/iso-notes.md` に記す。
- 多倍長整数（BIG タグ）。
- Cell の表現（ADR 0001/0002）と IR（ADR 0003/0009）の変更。

## 反目標（動いても失敗とみなすもの）

- GC が項を黙って壊し、誤った答えを返すこと。ヒープあふれで止まるより悪い。
- 普段の実行が目に見えて遅くなること（下の「速度」）。
- インタプリタと翻訳コードの答えが食い違うこと。
- `src/platform/` の外に OS 依存のコードを書くこと。

## 制約

- AGENTS.md の規則に従う。関数は 60 行以下、ファイルは 800 行以下。生の `new`/`delete`、`reinterpret_cast`、マクロは使わない。新しい依存ライブラリは足さない。
- 実装の前に ADR 0010（GC とヒープの伸長）を書き、所有者の承認を得る。承認の前にコードを書かない。
- ADR 0002: ヒープの語はすべてが項ではない。GC はヒープを線形に走査して語を項として扱わず、タグ付きポインタをたどる。
- ADR 0003: ゴール枠は項ではない。マークのルートに含めるが、項として走査しない。
- ADR 0009: `Ctrl::Native` 枠（語 1 の第 63 ビットが立つ）は、語 5 以降をセルとしてマークし、語 4（関数ポインタ）は項として読まない。
- 項のセルは実アドレスを持つ（`Heap::pointer`）。ゴール枠・継続・`redo_goal` はヒープの添字（`std::uint64_t`）で持つ。`Trail::slots` と `Trail::mark` は生ポインタ。詰め直しでは、この 3 種類をすべて書き換える。

## 決まったこと

### ヒープの伸長（所有者が方針を決め、作りは私の判断）

- 起動時に上限までの仮想アドレス空間を予約し、実際のメモリはそこから少しずつ確保する。確保した部分のアドレスは動かない。予約と確保は `src/platform/` に置く（POSIX は `mmap`+`mprotect`、Windows は `VirtualAlloc` の `MEM_RESERVE`/`MEM_COMMIT`）。
  - 理由: セルが実アドレスを持つので、配列を別の場所へ引っ越すと全ポインタの書き換えが要る。予約しておけば伸長は「確保を足す」だけになる。ビルトインの途中で容量が足りなくなっても、その場で伸ばせる。「ステップを巻き戻してやり直す」仕組みが要らない。
  - 所有者には途中で「GC のときに 2 倍の配列へ引っ越す」案を話した。利用者から見た振る舞い（自動で伸び、伸ばせなければ止まる）は同じで、作りだけをこちらに変えた（私の判断）。
- 上限は 2 段にする。
  - 利用者の上限: 環境変数 `MOSA_HEAP_MAX` と `mosa` の起動オプション（名前は実装者が決める）で指定する。既定は 4 GiB。Linux はメモリを使い切ると、メッセージを出す間もなくプロセスを殺すことがある。既定の上限は、その前に自分で止まるためにある。
  - OS の上限: 予約か確保を OS が断ったとき。
- 既存の `heap_limit` 引数（`Machine::create`、`run_session`、`main_mosa.cpp`、生成する `main.cpp` の `src/codegen/project_main.cpp:63`）は「伸ばせる上限（語数）」と読み替える。小さい値を明示している既存のテストは、上限を超えたときの振る舞いを確かめるテストとして、そのまま通るはずである。
- 上限の決め方（私の判断）: API の `heap_limit` 引数が渡された値をそのまま使う。環境変数は API の中では読まない（テストが環境に左右されないため）。入口（`mosa` の `main` と、生成する `main.cpp`）が「起動オプション → `MOSA_HEAP_MAX` → 既定 4 GiB」の順で値を決めて渡す。mosac の実行ファイルの引数は利用者のプログラムのものなので、実行ファイルに起動オプションは足さず、`MOSA_HEAP_MAX` だけを読む。
- 上限の意味（私の判断）: 「ヒープ全体の上限」であり、生きているデータに 1 ステップ分の余裕を足した量が入る。GC はステップの途中で走れないので、柔らかい容量 C は上限から余裕（たとえば上限の 1/4、ただし最低 64Ki 語。実装者が調整する）を引いた値を超えない。こうして、上限に当たる前に必ず安全点で GC の機会がある。
- 起動時に確保する量は今と同じ 2^20 語（8 MiB）とする。ただし上限がそれより小さければ上限に合わせる。

### GC の起動と伸長の方針（私の判断）

- GC は `run_loop` のステップとステップの間（安全点）でだけ走る。ビルトインと生成関数の途中では走らない。このため、ビルトインの C++ ローカル変数が握る Cell は動かない。
- 「柔らかい容量」C を持つ。安全点で使用量が C 以上なら GC を走らせる。GC の後で生きているデータが C の 7 割を超えていたら、C を 2 倍にする（上の「上限から余裕を引いた値」まで）。ステップの途中の確保は C を超えてよく、上限まで確保を足す（ヒープの伸長は確保を足すだけなので安い）。
- 安全点の検査は 1 回の比較にする。

### 方式（SPEC 第6節で決まっている mark-and-compact。細部は私の判断）

- マーク: ルートからポインタをたどり、生きている語に印を付ける。印はヒープとは別のビット表に持つ。語は 3 種類に分けて記録する。セル（ポインタなら書き換える）、生の語（浮動小数・IntBox の中身、関数語、Native 枠の語 4 など。書き換えない）、枠の添字（継続など。添字として書き換える）。
- 詰め直し: 順序を保ってずらす（sliding）。順序が保たれるので、選択点の `heap_mark` は「その位置より下の生きている語の数」に書き換えればよい。新しい位置はビット表と区画ごとの累計から計算する。具体的なアルゴリズム（LISP2 型か、ビット表＋区画の累計か）は実装者が決める。
- trail: 印の無いセルを指す項目は捨て、残りの項目のポインタを書き換える。選択点の `trail_mark` もそれに合わせて直す。`Trail::mark` も書き換える。

### ルート

調べた範囲では次のとおり。漏れが無いかを確かめるのは実装者の最初の仕事である（下の「ストレス試験」で機械的に確かめる）。

- `Impl::ip`、`ball`、`bindings`
- `stack` の各 `Entry`: `env`、`cont`、`redo_goal`、`pattern`、`heap_mark`、`trail_mark`
- `extras` の `Extra` のうち、到達できる制御枠（語 1 が extras の添字）から指されているものだけ: `env`、`cont`。全部をルートにはしない（下の「extras の回収」）
- trail（上の扱い）
- 継続でつながるゴール枠と制御枠（ADR 0003/0009 の配置に従って中をたどる）
- **入れ子の実行ループ**: 次の場所は、C++ の中で `run_loop` をもう一段まわす。
  - `findall/bagof/setof`（`src/builtins/solutions.cpp` の `collect`）
  - consult 中の指示（`src/machine/load_directive.cpp:498`）
  - `src/builtins/write_pred.cpp:596`。これは 2 つの道から呼ばれる。`with_output_to`（`:671`）と、`print` の portray フック（`apply_portray`、`:450`）である
  - `src/machine/lgt_copy.cpp:85`。ただしテストスイート用の道具の中で、別のマシン上で回すだけである

  入れ子が回っている間、C++ のローカルは Cell とヒープの水位とヒープの添字を握ったままである。具体的には次のもの。
  - `templ`、`witnesses`、`hidden`
  - `Saved` と `Snap` の中身（`extras_mark` を含む）
  - 読み込み器の `heap_base`
  - ビルトインが入れ子の後でも使う `Goal` の `at` と `cont`（`step` の `const Goal goal`、`engine.cpp:122`）
  - findall の `VarIds`（`Home.raw`/`index`、`stable`、`local`、`ext_raw`、`alias`。`solutions.cpp:45-88`）。生のアドレスとヒープの添字を解の間ずっと持つ

  これらを「ルートの登録簿」へ載せ、GC が書き換える。登録簿は `Impl` に持ち、登録はスコープで行って、抜けるときに外す。こうして findall の中でも GC を効かせる（私の判断）。入れ子の中で GC を止める案は捨てた。findall の中で重い計算をすると、負荷テストがまたあふれるからである。
- **例外: portray フックの中では GC を止める**（私の判断）。portray フックは writer の再帰の途中で走る。writer の C++ の枠は Cell を握っており、`Printer::assigned_`（`src/write/writer.cpp:256`）は生のアドレスを鍵にしている。この writer はフェーズ7の 2 番目の仕事で反復に書き直すので、今は GC を禁止する数を持ち、portray の間だけ GC を止める。`with_output_to` の道は普通に登録する。止めたことは GC のコードに書いておき、writer を書き直すときに外す。

### extras の回収（私の判断）

- インタプリタは、3 つ以上のゴールが並ぶ本体を 1 歩進めるたびに `Extra` を 1 つ積む（`launch` の `And` から `embody` を経て `push_extra`、`engine.cpp:387-415`）。`extras` が縮むのはバックトラック（`choice.cpp:44`）と新しい問い合わせ（`engine.cpp:546`）のときだけである。このため、ヒープを GC しても、インタプリタの `loop(N)` と `tak` は `extras` を通じて伸び続ける。
- そこで GC は `extras` も回収する。到達できる制御枠から指される `Extra` だけに印を付け、順序を保って `extras` を詰める。そのうえで、次の添字を書き換える。
  - 制御枠の語 1（extras の添字）
  - 選択点の `extras_mark`
  - 登録簿にある `extras_mark`（`Saved`、`Snap`、ビルトインのローカルの写し）

  バックトラックで `extras` を水位まで切り詰める今の作りは、順序を保つ詰め直しであればそのまま正しい。
- 実行モデルを変えて、ただの連言では `Extra` を作らないようにする案は捨てた。ADR 0003 の実行モデルに手が入るうえ、GC と別の大きな変更になるからである。
- 「頭打ち」の対象は、ヒープ、`extras`、trail の 3 つ全部である。選択点スタックは、決定的なループでは伸びない。伸びるなら、それは生きている選択点である。

### 安全な停止（所有者の要件、細部は私の判断）

- 上限に当たったら、ヒープを壊さずに今の問い合わせを止める。ヒープの上限と大きさを含むメッセージを日英で出す（ADR 0007 の文面カタログに鍵を足す）。REPL は生きたまま次の入力を待つ。mosac の実行ファイルは今と同じく終了コード 2 で終わる。
- trail・選択点スタック・ルートの登録簿など `std::vector` が OS からメモリをもらえなかったとき（`std::bad_alloc`）も、同じ停止にする。
- `catch/3` で捕まえられる `resource_error(memory)` にはしない。今の `heap_limit` の扱い（C++ の致命的エラー、SPEC 第6節）に揃える（私の判断）。

### 統計値の見せ方（所有者の要件、形は私の判断）

- `garbage_collect/0`: その場で GC を走らせる。
- `statistics/2`: 少なくとも次の鍵を持つ。SWI-Prolog に同じ鍵があれば、形をそれに揃える（揃えられるかは実装者が確かめる）。
  - `garbage_collection` → `[回数, 回収したバイト数, GC に使ったミリ秒]`
  - `heap` → `[使用バイト数, 柔らかい容量のバイト数, 上限のバイト数]`（Mosa 独自の鍵）
  - `runtime`、`walltime`、`cputime`（時間計測の基本。負荷テストの所要時間を測るため）
- GC ログの旗: Prolog の旗（名前は実装者が決める）を on にすると、GC のたびに標準エラーへ 1 行出す。内容は回数、GC の前後の使用量、容量、かかった時間。文面は日英のカタログに置く。既定は off。

## 試験

- 物差しの 2 本を、小さい上限（たとえば 2^16 語）で最後まで走らせる。インタプリタと翻訳コードの両方で行う。次のことを確かめる。
  - GC の回数が 1 以上であること（`statistics/2`）
  - 柔らかい容量が伸びていないこと（頭打ち。`statistics/2`）
  - `extras` と trail の長さが頭打ちであること。C++ のテストで `Impl` を直接見る
- 伸長: 数百万要素のリストを作って保持するプログラムが、上限が十分なら最後まで走り、容量が伸びることを確かめる。
- 停止: 上限を小さくしてあふれさせ、メッセージが出ること、REPL が次の問い合わせに答えること、実行ファイルが 2 で終わることを確かめる。
- 入れ子: `findall` の中で `loop(N)` を回しても完走し、結果が正しいことを確かめる。consult 中の指示の中で回す場合も同じ。
- **ストレス試験**: 環境変数（たとえば `MOSA_GC_STRESS=1`）で、安全点ごとに毎回 GC を走らせる。この下で既存の ctest と `mosatest --diff` を全部通す。ルートの登録漏れは、ここで答えの食い違いか異常終了として表に出る。CI では 1 つの OS（Linux）だけで、別ジョブとして回す（遅いため。私の判断）。
- 速度: `mosatest --bench` で、インタプリタと翻訳コードの速度が GC を入れる前より 5% 以上落ちないことを確かめる（私の判断）。`docs/bench.md` を更新する。

## 実装者に任せること

- sliding のアルゴリズムの選び方。ビット表と区画の大きさ。
- 起動オプションと旗の名前。
- 柔らかい容量の閾値（7 割、2 倍）の微調整。根拠を ADR 0010 に書く。
- GC のコードを置く場所（`src/core/` か `src/machine/` か）。ファイル分割は 800 行の規則に従う。
- タスクへの分け方。ただし「ADR 0010 の承認」→「ヒープの予約と伸長」→「マークと詰め直し（ルートの登録簿と extras の回収を含む）」→「ストレス試験を CI に入れる」→「`garbage_collect/0` と `statistics/2` とログの旗」→「物差しの試験と bench」の順は崩さない。各タスクの終わりで ctest が通ること。

## 背景

負荷テストは `heap_limit` で止まる。`tak(18,12,6)` はヒープがあふれ、素朴な `loop(N)` は N が 40000 から 45000 の間であふれる。インタプリタの `extras` と trail も、バックトラックでしか縮まないので伸び続ける。
セルは実アドレスを持ち（ADR 0001/0002）、ゴール枠・継続・`redo_goal` はヒープの添字を持ち（ADR 0003/0009）、`Trail::slots` と `Trail::mark` は生ポインタである。ヒープが動くと、このすべてを書き換えることになる。
持ち主の要望は、GC、自動で伸びるヒープ、伸ばせないときの安全な停止、見える統計値である。合格の目安はメモリの絶対値ではなく、SPEC 第9節の完了条件にある頭打ちである。

## 決定

ヒープ: `Heap` は起動時に上限までの仮想アドレス空間を予約し、必要に応じて下から確保する（POSIX は `mmap`+`mprotect`、Windows は `VirtualAlloc` の `MEM_RESERVE`/`MEM_COMMIT`。どちらも `src/platform/`）。確保済みのセルは動かないので、ビルトインはステップの途中でもヒープを伸ばせる。上限は語数で、`Machine::create` の `heap_limit` 引数をそのまま使う（API は環境変数を読まない）。入口（`mosa` の `main` と生成する `main.cpp`）は `--heap-max`（MiB の整数。`mosa` のみ）→ `MOSA_HEAP_MAX`（MiB）→ 既定 4 GiB（2^29 語）の順で決める。Linux の OOM killer はメッセージを出す前にプロセスを殺すことがあるためである。起動時の確保量は min(2^20 語, 上限) とする。安全点: GC は `run_loop` のステップとステップの間でだけ走り、ビルトインや生成関数の途中では走らない。このため、C++ のローカルが握る Cell は動かない。柔らかい容量 C（`gc_capacity`）は `limit - headroom` を超えず、`headroom = min(max(limit / 4, 65536), limit / 2)` 語とする。これで 1 ステップの確保が headroom より少なければ、上限の前に GC の機会がある。ステップの途中の確保は C を超えて上限まで進んでよい。安全点の検査は `gc_trigger` との比較 1 回である。`gc_trigger` は閾値 `gc_threshold`（普段は C）と同じ値で、`MOSA_GC_STRESS` のときだけ 0 にして、安全点のたびに遅い道へ入る。GC の後で生きているデータを L とする。L > 0.7·C である間、C を 2 倍にする（上限まで）。大きな 1 ステップの後でも GC は 1 回で済む。上限でもなお L > 0.7·C なら `gc_threshold = max(C, L + (limit - L) / 2)` とする。ヒープが埋まりかけても安全点ごとに GC せず、最後は上限で止まる。極端に小さい上限（`Machine::create(8)`）は、今までどおり `heap_limit` で止まる。
回収: 印付けは明示的なスタックで行い（C++ の再帰なし）、1 語 1 ビットの表に付ける。語ごとに 2 ビットで種類（Cell、Raw、FrameIndex、ExtrasIndex）も持つ。Str の関数語、Float と IntBox の語、ゴール枠の語 0〜2 は Raw、`Ctrl::Native` 枠の語 0〜2 と 4 は Raw、語 5 以降は Cell とする（ADR 0009）。詰め直しは sliding で、`rank(i)` は i より下の印の付いた語の数であり、64 語の区画ごとの累計と `popcount` で引く。ヒープを下から 1 回走査して、印の付いた語を `rank(i)` へ写し、Cell のポインタ、枠の添字、extras の添字を書き換える。順序が保たれるので、選択点の `heap_mark` は `rank(mark)` になる。`extras` は、到達できる制御枠から指されている項目だけを順序を保って残す（別のビット表）。trail は、スロットに印が付いた項目だけを残して書き換え、`trail_mark` は旧位置より下に残った項目の数にする。ルート: `ip`、`ball`、`bindings`、選択点スタックの各 `Entry`、`Trail::mark`、そして入れ子の C++ の持ち物を載せる登録簿 `Impl::gc_roots` である。入れ子の `run_loop` を回す場所（`findall/bagof/setof`、consult 中の指示、`with_output_to`）はすべて `RootScope` を持ち、Cell・ヒープの水位・ヒープの添字（findall の `VarIds`、読み込み器の `heap_base`、`extras_mark` を含む `Saved` と `Snap`）を登録して、抜けるときに外す。`lgt_copy` の道具は何も登録しない。その `run_loop` は別の作業用マシンの上で回り、ループの後でそのヒープを読むものは無く、その間に元のマシンは動かない（`src/machine/lgt_copy.cpp`）。portray フック（`src/builtins/write_pred.cpp` の `apply_portray`）だけは例外で、writer の再帰の途中で `GcInhibit` の数が GC を止めていた。ADR 0011（2026-10-30 承認）でこれを外す。繰り返しで動く writer は、積んだ仕事と表を `RootScope` で知らせる。
空きを生まない GC（2026-10-30 改訂、所有者の決定 B）: C が上限側の天井にあるときに、安全点が `heap.size()` が `gc_threshold` に達したことで始めた GC を数える。前に判定した回収から空いた語（`gc_stats.freed_words` のそのときの値との差。間に `MOSA_GC_STRESS` や `garbage_collect/0` が空けた分も入る）が `limit / 32` より少なければ空きを生まなかったとし、空きを生んだ GC は数を 0 に戻す。空きを生まない GC が 3 回続いたら、安全点は回収の後、ステップとステップの間で、上限での確保と同じ `ResourceLimit("heap_limit")` を投げ、下の停止と同じ扱いになる。`MOSA_GC_STRESS` や `garbage_collect/0` が起こした GC は判定しない。数と基準はトップレベルの問い合わせ・`consult`・`load_program` のたびに戻し、数は C が天井より下のときにも 0 に戻す。停止: 上限に当たったとき、確保を OS に断られたとき、`std::bad_alloc` のときは、ヒープを壊さずに今の問い合わせを止め、日英のメッセージを出す（ADR 0007 のカタログ）。REPL は続け、`mosac` の実行ファイルは 2 で終わる。`catch/3` では捕まえられない。今の `heap_limit`（`ResourceLimit`）と同じである。

## 捨てた案

GC のときに 2 倍の配列へ引っ越す案。セルが実アドレスなので全ポインタ・trail のスロット・添字を書き換えることになり、ステップの途中では伸ばせない（ステップを巻き戻す手立てが無い）。
入れ子の `run_loop` の中では GC を止める案。`findall` の中の重い計算がまたあふれ、直したい失敗がそのまま残る。
実行モデルを変えて、ただの連言で `Extra` を作らないようにする案。ADR 0003 に手が入り、GC と別の大きな変更になる。GC が `extras` を回収すれば足りる。上限の近くでも回収を続ける案（A、改訂前の形）。GC は 1 回ごとに O(L) かかり、空けられる量は減っていくので、止まらずに這うように遅くなる。Java も同じように止める（"GC overhead limit exceeded"）。

## 影響

承認のときに、SPEC 第6節（英日）の Heap と GC の行を、「`std::vector<Cell>` で上限まで確保する」から、予約したアドレス範囲を必要に応じて確保する形へ改め、`docs/iso-notes.md`（英日）にアトム表の GC は無く、アトムを作り続けるループでは表が伸びることを記す。ヒープ・`extras`・trail は頭打ちになり、選択点スタックは生きている選択点の分だけ伸びる。`statistics/2`、`garbage_collect/0`、ログの旗は後のタスクで入れる。承認の前にこの ADR のコードは書かない。
改訂の後は、生きているデータと上限の差が `limit / 16` ほどより小さいままのプログラムは、ゆっくりなら終わったはずでも、3 回の GC の後に上限のメッセージで止まる。対処は `--heap-max` / `MOSA_HEAP_MAX` を大きくすることである。
生きているデータが伸び続けるプログラムは、止まるまでの間、空きを生む回収（1 回に `limit / 32` 以上を空ける）の費用をなお払う。

## 改訂 2（2026-11-02、レビュー M6、所有者の決定 A）

背景: findall/3、bagof/3、setof/3 は、答えを 1 つずつヒープの外の C++ の節点（ADR 0013 の `ExportedTerm` と `Image`。`f(X,X,X)` で RSS 約 360 バイト）として持つ。上限はヒープの語だけを数えていたので、`--heap-max 16` でも `findall(f(X,X,X), between(1,10000000,X), L)` は OOM killer の前に 3.6 GB まで育った。
決定: 動いている収集は、残した答えと鍵のバイト数（ベクタの容量と、それらを入れるベクタが伸びた分を含む）を 8 で割って切り上げ、`Heap::held()` に足し、`Collecting` の状態が壊れるとき（終わり、例外、問い合わせの破棄）に返す。持っている語はどこでもヒープの語と同じに数える。確保の速い道は `min(commit 済み, limit - held)` で止まり、ヒープを伸ばすのは `size + held + count > limit` で止まり、安全点は `size + held` を `gc_threshold` と比べ、答えを足して `size + held` が上限を超えたら同じ `ResourceLimit("heap_limit")` を投げる。`gc_capacity` は今までどおり生きている語だけで広げ、方針を決めるたびにその写しを `live + held`（閾値と空きを生まない GC の判定の L。GC と GC の間の `live` は前の GC の後に生きていた語で、判断のときにヒープがそれより小さければ、バックトラックで消えたのでその大きさまで下げ、後のゴミを生きている語に数えないよう次の GC まで下げたままにする）に合わせて広げる。そのため持った語で広げた C は収集の後に残らず、何も持っていなければ判断はどれも改訂前と同じになる。
捨てた案: B（答えを 8 バイトの語の平らな配列でも持つ。密度は約 10 倍）は変更が大きいので後に回す。組み直したときに要るヒープの語で数える案は、RSS は C++ の大きさなので、上限を約 10 倍超えうる。影響: 同じ `--heap-max` で持てる答えは、ヒープの語で持つ場合の約 1/10 になる。節の格納、選択点のスタック、そのほかの C++ の状態は数えないまま（レビュー M17）。

## 改訂 3（2026-11-03、レビュー M17。M17 を直す依頼で承認）

背景: 選択点のスタック（`Entry`。libc++ で 248 バイト）、`extras`（`Extra`。96 バイト）、節の呼び出しと call/1 のゴールごとの env（`EnvCells`）、call/1 とその仲間が実行時に訳す IR は、ヒープの外の C++ の物である。そのため `p :- (p ; true).` は `--heap-max 1` でも止まらずに 8 秒で RSS 2.2 GB に達し、`p :- p, true.` は 64 MiB の上限で止まったが RSS は 567 MB だった。
決定: `Heap::state()` がこれらを語で数える（バイト数を 8 で割って切り上げる）。`stack`、`extras`、`scan_log` は、最後に容量を返してから持った要素の数の最大を数える（容量は倍々に伸びるので、数えると止まる所が上限の半分ずれる）。env と実行時に訳したゴールは 1 つずつ（`sizeof`、持っているバッファ、参照の数 2 つ）を、作るときに足し、放すときに引く。選択点が持つ候補の列は、語を足し引きするアロケータで数える。状態の語は、安全点（速い道は `size + state` を trigger と比べる。答えを返す前にも通る）と GC の方針で持った語と同じに数える。GC が空けた状態の語は、空きを生まない GC の判定で空いた語に入れる。GC の後もなお `size + held + state` が上限を超えていれば、安全点は同じ `ResourceLimit("heap_limit")` を投げる。GC は入れ子の実行の中でも、大きさの 4 倍を超えたベクタの容量を返す。
捨てた案: 確保のたびに状態を確かめる案。確保の速い道がそれを読むことになり、歩みごとの安全点で超える量は 1 歩分に収まる。env と IR を作るときに数え、GC のときにだけ数え直す案。失敗で回るループが、バックトラックですでに空いたゴミのために GC することになる。trail（どの項目も束縛したヒープか env のセルなので、数えた語より少ない）、節の格納（実行の状態ではなくデータベースで、SWI-Prolog もスタックの上限の外に置く）、consult の指示が脇に置いたスタックは数えない。影響: 同じ `--heap-max` で持てる生きた選択点と枠は前より少ない（16 MiB で、1 歩ごとに選択点を残す再帰は 987,000 歩ではなく 46,000 歩で止まる）。1 歩の中では、次の安全点まで状態が上限を超えることがある。ヒープに比べて継続と env が大きいプログラムは GC が増える（`tak` は 0 回が 100 回になり +3.7%。bench.md）。

## 改訂 4（2026-11-20、レビュー H-02。H-02 を直す依頼で承認）

背景: 単一化（`src/core/unify.cpp` の `Attempt::seen`）と標準順序（`src/builtins/order.cpp` の `PairSeen`。`==`、`compare/3`、`@<`、並べ替えの下にある）は、入った複合項の組を、最初の 256 の後はヒープの外の C++ の集合に覚える。`a` だけの巡回リストを、互いに素な周期 p と p+1 で 2 つ作ると、組は p·(p+1) になる。p=2000 では 104,125 語のヒープに対して組が 4,002,000 で、`--heap-max 16` でも RSS が 238 MB になり、p≈17,000 で約 16 GiB に届く。同じ組に戻らない歩みが入る組は複合項のセルより少ない。100 万要素の基底のリスト 2 つの `L = M` は、6,000,020 語のヒープに対して組が 1,000,000 である。
決定: 1 つの共有の表（`src/core/pair_memo.hpp`）が、使っているヒープの語の数までの組は数えず、それを超えた組を、足すたびにその場で確かめる。1 組を 40 バイト（組、次への指し手、ハッシュの値、桶の指し手 1 つ）とし、語に切り上げる。`size + held + state` にその語を足して上限を越えるなら、同じ `ResourceLimit("heap_limit")` を投げるので、1 歩の中で止まる。`unify`（`src/core/unify.cpp`）は、ほかの投げ方と同じく抜けるときに束縛を戻す。`subsumes_term/2` と `unify_with_occurs_check/2` は同じ単一化を通る。`term_equal`（実行器の変種の判定）の組は変数の組で、複合項の組ではなく変数の数で伸びるので、数えない。
捨てた案: 組を全部数える案。普通の大きなリスト 2 つの `L = M` や `L == M` がヒープの約 2 倍を要るようになり、16 MiB で通る一番大きなものが約 300,000 要素から縮む。単一化と `==` を複合項のセルの union-find にする案。表はセルの数に比例するが、ADR 0011 の改訂 1 のよく通る歩き手を変え、`compare/3` の順序を保つことは示していない（最初の違いがある組を飛ばしうる）。別の項目にする。安全点でだけ確かめる案。単一化は 1 回で 1 歩である。
結果: 数えない分はたかだか使っているヒープの語の数 × 40 バイト ÷ 8 なので、止まる所はちょうど上限ではなく、上限にヒープに比例する分を足した所になる。組がヒープの語の数より少ない歩み（測った巡回しない歩みは全部）は前と同じに動く。互いに素な周期の巡回する 2 つの項は、上限まで 2 乗の時間をかけてからヒープの上限で止まる（`--heap-max 16` の p=2000 は、成功する代わりに止まる）。

Status: Approved (2026-10-30). Amended 2026-10-30 (owner decision B): unproductive GC near the limit stops the query. Amendment 2 (2026-11-02, review M6, owner decision A; approved by the owner's request to implement M6): words held by running collections count against the limit.

## Context

Load tests stop at `heap_limit`: `tak(18,12,6)` overflows the heap and a bare `loop(N)` overflows between N = 40000 and 45000, and the interpreter's `extras` and the trail also grow without bound because they shrink only on backtracking.
Cells hold real addresses (ADR 0001/0002), while goal frames, continuations and `redo_goal` hold heap indexes (ADR 0003/0009) and `Trail::slots` and `Trail::mark` are raw pointers, so a heap that moves needs every one of them rewritten.
The owner asked for a GC, a heap that grows by itself, a safe stop when it cannot, and visible statistics; the plateau is the exit check of SPEC section 9, not an absolute size.

## Decision

Heap: `Heap` reserves virtual address space up to the limit at start-up and commits it from the bottom as needed (`mmap`+`mprotect` on POSIX, `VirtualAlloc` `MEM_RESERVE`/`MEM_COMMIT` on Windows, both in `src/platform/`), so committed cells never move and a built-in can grow the heap in the middle of a step. The limit is in words: the `heap_limit` argument of `Machine::create` as given (the API reads no environment variable); the entry points (`mosa`'s `main`, generated `main.cpp`) decide `--heap-max` (MiB, an integer; `mosa` only) → `MOSA_HEAP_MAX` (MiB) → default 4 GiB (2^29 words), since the Linux OOM killer can kill the process before it prints a message. The initial commit is min(2^20 words, limit).
Safe points: GC runs only between two steps of `run_loop`, never inside a built-in or generated function, so a C++ local that holds a Cell is never moved. A soft capacity C (`gc_capacity`) is at most `limit - headroom` with `headroom = min(max(limit / 4, 65536), limit / 2)` words, so a GC opportunity comes before the limit whenever one step allocates less than the headroom; allocation inside a step may pass C up to the limit. The check at a safe point is one comparison against `gc_trigger`, which equals the threshold `gc_threshold` (C normally), or 0 under `MOSA_GC_STRESS` so that every safe point takes the slow path. After a GC with live data L: while L > 0.7·C, C doubles up to the cap, so one large step costs one GC; if L > 0.7·C still holds at the cap, `gc_threshold = max(C, L + (limit - L) / 2)`, so a nearly full heap does not collect at every safe point and the run ends at the limit instead. A tiny limit (`Machine::create(8)`) keeps today's `heap_limit` stop.
Collector: mark in an explicit stack (no C++ recursion) into a bit table, one bit per word, plus 2 bits per word for the kind (Cell, Raw, FrameIndex, ExtrasIndex): Str functor words, Float and IntBox words and goal-frame words 0-2 are Raw, a `Ctrl::Native` frame's words 0-2 and 4 are Raw and its words from 5 are Cells (ADR 0009). Then slide: `rank(i)` = marked words below i, from per-64-word block prefix counts plus `popcount`, one upward pass moves each marked word to `rank(i)` and rewrites Cell pointers, frame indexes and extras indexes, so order is kept and every `heap_mark` becomes `rank(mark)`. `extras` keeps only entries that a reachable control frame points to, in order (own bit table); the trail keeps only entries whose slot is marked and rewrites them, and each `trail_mark` is the number of kept entries below its old position.
Roots: `ip`, `ball`, `bindings`, every `Entry` of the choice stack, `Trail::mark`, and `Impl::gc_roots`, a registry of nested C++ holders. Every site that runs a nested `run_loop` (`findall/bagof/setof`, directives while consulting, `with_output_to`) holds a `RootScope` that registers its Cells, heap marks and heap indexes (findall's `VarIds`, the loader's `heap_base`, `Saved`, `Snap` with `extras_mark`) and deregisters on exit. The `lgt_copy` helper holds none: its `run_loop` runs on a separate scratch machine, nothing reads that machine's heap after the loop, and the outer machine does not run meanwhile (`src/machine/lgt_copy.cpp`). The portray hook (`apply_portray` in `src/builtins/write_pred.cpp`) was the one exception, a `GcInhibit` counter stopping GC inside the writer's recursion; ADR 0011 (approved 2026-10-30) removes it, since the iterative writer registers its pending work and tables with a `RootScope`.
Unproductive GC (Amended 2026-10-30, owner decision B): a GC that the safe point starts because `heap.size()` reached `gc_threshold` while C is at its cap is counted; it is unproductive when fewer than `limit / 32` words were freed since the last judged collection (`gc_stats.freed_words` minus its value then, so words freed in between by `MOSA_GC_STRESS` or `garbage_collect/0` count too), and a productive one resets the count to 0. At 3 unproductive GCs in a row the safe point throws, after the collection and between two steps, the same `ResourceLimit("heap_limit")` as an allocation at the limit, so the same stop below follows. GCs forced by `MOSA_GC_STRESS` or `garbage_collect/0` are not judged, and the count and the baseline are reset at every top-level query, `consult` and `load_program`; the count also returns to 0 whenever C is below its cap.
Stop: reaching the limit, a refused commit or a `std::bad_alloc` stops the current query without damaging the heap, with a bilingual message (ADR 0007 catalog); the REPL continues, a `mosac` executable exits 2, and `catch/3` cannot catch it, as with `heap_limit` today (`ResourceLimit`).

## Rejected alternatives

Moving to an array twice as large at GC time, since cells are real addresses, so every pointer, trail slot and index would be rewritten and the heap could not grow in the middle of a step (no way to undo a step).
Switching GC off inside nested `run_loop` calls, since a heavy computation inside `findall` would overflow again, which is the failure being fixed.
Changing the execution model so that a plain conjunction creates no `Extra`, since it changes ADR 0003 and is a large change apart from GC; collecting `extras` in the GC does the job.
Keeping on collecting near the limit (A, before the amendment): each GC costs O(L) and frees less and less, so the program slows towards a crawl instead of stopping; Java stops the same way ("GC overhead limit exceeded").

## Consequences

On approval, SPEC section 6 (English and Japanese), rows Heap and GC, change from "allocated as `std::vector<Cell>` with an upper bound" to a reserved address range committed as needed, and `docs/iso-notes.md` (English and Japanese) records that there is no atom table GC, so a loop that makes atoms grows the table. Heap, `extras` and trail all plateau; the choice stack grows only with live choice points. `statistics/2`, `garbage_collect/0` and a log flag follow in a later task. No code is written on this ADR before it is approved.
Since the amendment, a program whose live data stays within about `limit / 16` of the limit is stopped with the heap-limit message after 3 GCs, even if it would have finished slowly; the remedy is a larger `--heap-max` / `MOSA_HEAP_MAX`.
A program whose live data keeps growing still pays for the productive collections (each freeing at least `limit / 32`) on its way to the stop.

## Amendment 2 (2026-11-02, review M6, owner decision A)

Context: findall/3, bagof/3 and setof/3 keep each answer outside the heap as C++ nodes (ADR 0013, `ExportedTerm` and `Image`, about 360 bytes of RSS for `f(X,X,X)`), so `--heap-max 16` let `findall(f(X,X,X), between(1,10000000,X), L)` reach 3.6 GB before the OOM killer; the limit counted heap words only.
Decision: a running collection adds the bytes of each kept answer and key (vector capacities included, also the growth of the vectors that hold them), divided by 8 and rounded up, to `Heap::held()`, and gives them back when its `Collecting` state is destroyed (finish, exception, query drop); held words count as heap words everywhere: the allocation fast path stops at `min(committed, limit - held)` and heap growth at `size + held + count > limit`, the safe point compares `size + held` with `gc_threshold`, and adding an answer that makes `size + held` pass the limit throws the same `ResourceLimit("heap_limit")`. `gc_capacity` still grows from live words only; each policy decision widens a copy of it for `live + held` (L for the threshold and the unproductive-GC judgement; between GCs `live` is the last GC's live words, lowered to the heap size whenever a decision finds the heap smaller, since backtracking freed them, and kept lowered until the next GC so that later garbage is not counted as live), so a C widened by held words does not outlast the collection, and with nothing held every decision is the one before this amendment.
Rejected: B (also store answers as a flat array of 8-byte words, about 10 times denser), a larger change kept for later; counting answers by the heap words they will need when rebuilt, since RSS is the C++ size, so the limit would still let RSS pass it by about 10 times. Consequences: the same `--heap-max` holds about 10 times fewer answers than heap words would; the clause store, the choice stack and other C++ state stay outside the count (review M17).
